# ConsentOSINT Phase 1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the secure local core for creating, authorizing, auditing, expiring, and deleting ConsentOSINT cases without implementing any external lookup or production OSINT adapter.

**Architecture:** A loopback-only FastAPI application and a local CLI share typed domain services backed by SQLAlchemy 2 and SQLite. Sensitive case fields are envelope-encrypted with keys obtained from an injected key provider; all mutations pass through the authorization policy and a PII-minimized HMAC audit ledger. Phase 1 has no outbound networking, uploaded-file processing, research frontier, source plugins, or browser UI.

**Tech Stack:** Python 3.12, FastAPI, Pydantic 2, SQLAlchemy 2, Alembic, SQLite WAL, `cryptography` AES-GCM, `keyring`, Argon2/token hashing where needed, HTTPX, pytest, pytest-asyncio, Hypothesis, Ruff, mypy, uv

**Spec:** `docs/superpowers/specs/2026-10-14-consentosint-design.md`

## Global Constraints

- Runtime is Python 3.12; the app binds only to `127.0.0.1` and supports one local user.
- Internal identifiers and code are English; user-facing messages and reportable policy text are Danish-first and localization-ready.
- Phase 1 performs no outbound network access and contains no OSINT source adapter.
- Telemetry is absent, not merely disabled; logs accept only allowlisted structured fields and never raw purpose, authorization references, or identifiers.
- Authorization bases are `self`, `explicit_consent`, `organizational`, and `synthetic`; external work is impossible unless a case is active and unexpired.
- Default retention is 30 days, accepted range is 1–180 days, and v1 has no override above 180 days.
- All timestamps are timezone-aware UTC; IDs are UUID4 generated by the application before encryption.
- Automated tests use only invented names and reserved domains under `example.com`, `example.org`, and `example.net`.
- SQLite is configured for WAL, foreign keys, a five-second busy timeout, restrictive file permissions where the OS supports them, and Alembic-managed schema changes.
- Standard SQLite is not represented as fully encrypted: sensitive fields use AES-256-GCM envelope encryption and documentation requires OS full-disk encryption; SQLCipher is not part of Phase 1.
- Master, audit, and API-session keys are separate key purposes and are never stored in SQLite, source code, ordinary logs, or command history. Each case has a random data-encryption key stored only in master-key-wrapped form.
- The public repository uses Apache-2.0 and includes an Abuse and Safety Policy before application code is merged.
- Dependencies are resolved into `uv.lock`; CI and documented installs use `uv sync --frozen`.
- Each task is committed only after its focused tests, Ruff, and mypy checks pass.

## Review Focus

- A case whose authorization expires between request validation and transaction commit must fail closed; Task 5 adds `test_authorization_expiring_during_create_rolls_back` using an injected clock advanced inside the transaction.
- Unicode purpose/reference text must round-trip through encryption without appearing in SQLite bytes or logs; Task 3 adds `test_unicode_sensitive_fields_are_encrypted_at_rest` and Task 5 adds `test_case_input_never_appears_in_logs`.
- Two audit appends racing for the same sequence must yield a single valid chain without duplicate sequence numbers; Task 4 adds `test_concurrent_appends_preserve_chain_order`.
- Deleting one case must not make another case's opaque audit scope correlatable or break ledger verification; Task 6 adds `test_delete_one_case_preserves_other_case_and_audit_chain`.
- API and CLI must reject malformed UUIDs, unknown enum values, naive datetimes, duplicate idempotency keys, and retention boundaries consistently; Tasks 1, 5, 7, and 8 pin these cases.
